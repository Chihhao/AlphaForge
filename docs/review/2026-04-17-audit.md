# 2026-04-17 Alpha Miner 資料層全面 Audit

`文件版本: 2026-04-17a`

## TL;DR

使用者看到 4/17 UI 推薦只顯示三支且全為首次推薦，要求全面 review + 今晚自動修復。原因是後端資料層 (scheduler 寫死維度、全輸過濾讀錯表、picks 前視偏差) 累積的一連串 bug 使 5d/10d 訊號與真實推薦歷史長期殘缺，連帶 UI 展開區 stock_perf 讀不到足夠樣本。

核心修復已上生產：資料層三大 bug 修正、缺漏訊號走 walk-forward 補齊、picks 重建覆蓋 4/1~4/17、backend image 重建完成。今日三維度訊號與推薦資料現已齊全且無前視。

## 發現的問題 (H = High, M = Medium)

### H1. `_generate_direction_picks` entry_price 前視偏差 (已於 commit 8819d07 修)

- 症狀：2025-09-03 的 2308 台達電 pick 記錄 entry_price=1840 (= 2026-04-17 當日收盤)，而非 680 (當時實收)。
- 根因：price_map 子查詢用 `StockPrice.date == (SELECT MAX(date) FROM stock_price WHERE stock_id=r.stock_id)` 但沒加 `<= latest_date` filter，導致 walk-forward backfill 時所有歷史 pick 都被寫成「今天」收盤價。
- 修復：在子查詢加 `StockPrice.date <= latest_date`。production daily 不受影響 (latest_date == today，行為等同)；walk-forward backfill 全部重跑。
- 驗證：2308 2025-09-03 entry_price=680 ✓。

### H2. Scheduler 三處 save_today_signals 寫死 `["20d"]` (已修)

- 症狀：alpha_signal_history 從 2026-04-02 起，5d 只剩零星紀錄、10d 完全斷層。
- 根因：commit 89ca3bb (4/10) 擴充 AlphaMinerService.DIMENSIONS 為 `[5d, 10d, 20d]`，但 `backend/app/core/scheduler.py` 的三個 `for dim in ["20d"]:` 迴圈 (line 218/285/344) 沒同步改。這三段是 9f3e869 與 1851b07 之前砍多維時留下的硬寫字串。
- 修復：在 scheduler 頂層加 `SIGNAL_DIMENSIONS = ["5d", "10d", "20d"]` 常數，三處迴圈統一用此常數。Job 名稱從 `"Save today alpha signals to history (20d long)"` 改為自動拼接版。
- 驗證：container 重建後，grep SIGNAL_DIMENSIONS 三處皆生效；4/17 三維度 alpha_signal_history 皆有紀錄。

### H3. `_generate_direction_picks` 全輸過濾讀錯表 (已修)

- 症狀：step 6.5 全輸過濾用 `_load_stock_perf_map` 從 `strategy_miner_trades` (舊假回測表) 讀歷史平均報酬，但 UI 顯示的 stock_perf 來自 `_load_stock_perf_from_picks` (真實 picks 歷史)。同一個「過去表現」概念被兩個函數用不同資料源解讀，導致上層 UI 看到「首次推薦」的股票仍被過濾、反之亦然。
- 修復：step 6.5 改呼叫 `_load_stock_perf_from_picks`，與 UI 顯示邏輯同源。
- 驗證：4/17 picks 重跑後，stock_perf 有值的推薦 (3710, 5228) 與 UI 實際看到的一致。

### M1. 20d long 訊號歷史缺口 2025-09-01~2026-03-31 (暫不處理)

- 現況：20d 在 4/1 才開始有資料 (12 天)，5d/10d 有 153/154 天 (2025-09-01 起)。
- 影響：20d 的真實推薦歷史勝率計算無法回溯到 4/1 之前，展開卡片顯示 trades 偏少 (目前記憶 `project_next_steps.md` 已記錄「20d trades 僅 26 筆」)。
- 暫不處理：補 20d 前 7 個月需 15 個 walk-forward checkpoint，時間成本高；用戶目前可接受累積 (已有 UI 警告 banner，commit f9fe697)。

### M2. `update_signal_returns` 用日曆日判定到期 (暫不處理)

- `alpha_miner_service.py:1113` 判定邏輯：`(today - signal_date).days >= HOLDING.get(dim, 30)`
- HOLDING={"20d": 30}，其他 dim 走 default 30。應該用交易日 (~20~30 calendar 差別小，但嚴格來說不對)。
- 影響：長假期 (春節 7-10 天) 訊號結案日期會偏早幾天，可能用到非交易日的 forward price；`_find_price` fallback 邏輯會往後最多 20 天找，實際影響小。
- 後續：列入 P3 技術債，等 20d 樣本累積後一起重新驗算。

### M3. AlphaMinerSnapshot 永遠只 1 row (已確認非 bug)

- `_save_snapshot` 每次 `db.execute(delete(AlphaMinerSnapshot))` 只保留最新一筆。
- 前端現已改用 `strategy_miner_*` 表不依賴 snapshot，設計本就是 1-row-latest。
- 備注：後續若要做模型歷史追蹤 (rolling IC、穩定性監測) 需改為 append 設計。

### M4. `strategy_miner_trades` 舊假回測表仍存在 (暫不處理)

- 僅留 legacy；H3 fix 後已不再被 picks 生成邏輯讀取。
- 之後若確認無其他 query 引用可以 drop；目前低優先級。

## Walk-Forward 補資料執行紀錄

### 1. 訊號 backfill (`scripts/backfill_signal_history_walkforward.py`)

```
checkpoint=2026-04-01  dims=[5d, 10d]  targets=11 個交易日
→ 寫入 1060 筆
```

訓練切分：train_end=2025-09-01, test_start=2025-10-01 (以 4/1 為 max_date 往前推 6m test + 1m gap)。per-date pct rank 無跨日污染。

### 2. Picks backfill (既有 `scripts/backfill_picks_history_walkforward.py`)

```
--start 2026-04-01 --interval 14
checkpoints = [4/1, 4/15, 4/17]
→ 寫入 51 筆 (4/1-4/17 每日 Top5)
```

### 3. 最終分佈驗證

| 維度 | signal_history 4/1~4/17 | picks 4/1~4/17 |
|---|---|---|
| 5d long  | 11 天 × 50 筆 = 550 筆 | 分佈於 4/2~4/14、4/17 |
| 10d long | 11 天 × 50 筆 = 550 筆 | 4/1 |
| 20d long | 12 天 × 20-29 筆 = 266 筆 | 4/15~4/17 |

維度分佈呈「某 checkpoint 只有一個維度過 quality gate」的塊狀，屬 walk-forward 合理行為，非資料錯誤。
